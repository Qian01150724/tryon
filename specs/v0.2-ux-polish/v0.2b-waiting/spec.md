# Spec: v0.2b 等待体验优化

## 1. 背景与目标

v0.1 的生成等待状态只有一个旋转加载圈，缺乏进度感知与用户控制。v0.2b 目标是让等待过程"可感知、可控制"：用户能看到当前进展，能主动取消，不会因为超时而一直干等。

## 2. 用户故事 / 使用场景

- **进度感知**：用户点击生成后，看到分步文字提示和进度条，知道 AI 正在做什么，不会误以为卡死
- **主动取消**：用户改主意或上传错图，点"取消"立即回到初始状态，不需要刷新页面
- **超时保护**：网络异常或服务慢，30 秒后自动中断，页面出现"超时，请重试"提示，用户一键重试

## 3. 功能需求 (FR)

| 编号 | 需求 | 验证方式 |
|------|------|---------|
| FR-001 | 生成中展示 5 条动态提示语，每 2 秒切换一次，循环滚动 | 点击生成后，每隔 2 秒文字更新一次 |
| FR-002 | 进度条采用 ease-out 曲线增长，基于预期时长计算，最高停在 90%，生成完成后才消失（不跳到 100%） | 等待过程中进度条持续增长，始终 ≤ 90%；结果出现后进度条消失 |
| FR-003 | 生成中显示"取消"按钮，点击后通过 AbortController 中止请求，页面回到初始 idle 状态 | 点取消后，加载状态消失，上传区和生成按钮恢复可操作 |
| FR-004 | 请求超过 30 秒自动触发 AbortController.abort()，显示超时错误提示"生成超时（超过 30 秒），请重试"，附带重试按钮 | 模拟网络延迟 > 30 秒，页面出现超时提示，无需刷新可重试 |

## 4. 成功标准 (SC)

| 编号 | 标准 |
|------|------|
| SC-001 | 生成期间文字每 2 秒切换，5 条提示语依次出现后循环 |
| SC-002 | 进度条在整个等待过程中始终 ≤ 90%，不出现跳到 100% 的情况 |
| SC-003 | 点取消后 stage 变为 `"idle"`，error 清除，加载圈和取消按钮消失 |
| SC-004 | 30 秒后 error 文本为"生成超时（超过 30 秒），请重试"，重试按钮可触发新一轮生成 |
| SC-005 | 生成完成（成功或失败）后，文字切换计时器和进度条计时器均被清除，无内存泄漏 |

## 5. 范围与边界

**In Scope**
- `components/ResultDisplay.tsx`：加载状态的提示语、进度条 UI 与 useEffect 定时逻辑
- `components/GenerateButton.tsx`：生成中状态下的取消按钮渲染
- `app/page.tsx`：AbortController 管理、30 秒超时逻辑、`handleCancel()` 函数

**Out of Scope**
- 结果展示（对比滑动条、放大弹窗）：属于 v0.2c 范畴，`ResultDisplay.tsx` 中已实现但不在本轮文档范围
- 上传区交互：已在 v0.2a-upload 落地
- 服务端超时处理：30 秒超时仅在客户端实现，服务端保持现状

## 6. 依赖与约束

- 依赖浏览器原生 API：`setInterval`、`clearInterval`、`AbortController`、`AbortSignal`
- 进度条逻辑依赖 `EXPECTED_MS = 8000`（预期生成时长 8 秒）作为曲线参考基准；实际生成时长不影响进度条行为（最高停 90%）
- `stage` 状态（`"idle" | "queued" | "processing" | "done" | "error"`）由 `page.tsx` 管理，`ResultDisplay` 通过 `isLoading`（`stage === "queued" || stage === "processing"`）prop 感知
- 超时计时器与 AbortController 在同一 `handleGenerate()` 闭包内管理，`handleCancel()` 只调用 abort，不处理计时器（计时器在 catch 分支的 `clearTimeout` 里清除）

## 7. 待澄清事项

无。所有功能点已在代码中完整实现，brief 与代码一致。
